## 0. 读法与目标

本轮美化**不动交互、不动滚动镜头、不动章节结构**，只回答五件事：

1. **模型本身**：白盒感还在——大量表面是纯白 / 浅灰，缺颜色也缺细节贴图，如何系统地上色；
2. **樱花树**：新增一棵樱花树，放在哪、长什么样、要不要落瓣；
3. **轨道电车**：商店侧边新增一辆垂直于道路停放的有轨电车与轨道；
4. **背景**：天空只有一条渐变，缺远景层次，如何补天际线等背景元素；
5. **昼夜降水**：白天不再落雨、改为樱花树落瓣（樱吹雪），夜晚落雨；雨滴落地的波纹样式重做（现状太丑）。

约束沿用项目硬约束（AGENTS.md §5）：亮色优先、两套明暗 tokens、`prefers-reduced-motion` 降级、粒子层 `pointer-events: none`、完成后 `mkdocs build` 验证、场景内无 HUD。

## 1. 阶段截图诊断（现状为什么显得「没上色」）

依据 `.documents/阶段截图/阶段5-*` 与阶段 6/7 截图逐机位核对：

| 观察 | 截图证据 | 根因（代码） |
|---|---|---|
| 店面墙体、屋顶、雨棚是一整片白 | 阶段5-亮色-全景 / 街角 | `materials.mjs` 里 `building: toon("#ffffff")`，白天 `set.building.color.copy(card)`（card=白）；墙体 / 屋顶 / 雨棚 / 邻栋**共用同一份材质**，无法分别给色 |
| 邻栋是无窗的白盒子 | 阶段5-亮色-全景 左侧 | 邻栋只用 `box()` + `mats.building`，没有任何窗格贴图 |
| 街景道具清一色灰 | 全景 / 街角：灯杆、护栏、自行车、路牌杆、雨伞架 | 全部走 `mats.trim`（`#7d8388`）或 `mats.fixture`（近白） |
| 白天画面整体发灰发飘 | 阶段5-亮色-全景 | `RAMP_DAY = [0.62, 0.71, 0.84, 0.97]` 分档偏亮 + hemi 1.6，白色反照率被进一步抬白；有颜色的只有店招、海报、贩卖机商品、盲道黄 |
| 夜里除了店招与店内，外墙全黑 | 阶段5-暗色-街角 | 夜景 `building` 被推向 `#3a4458` 暗色，但**没有窗光、没有分色、没有屋顶设备**，立面失去信息量 |
| 天空只是一条素渐变 | 全景上半屏 | `createSky()` 只画 1×256 竖直渐变；设计文档 §4.3 提过「远景楼宇 `rgba(62,82,112,0.2)`」但代码从未落地，场景里没有任何远景几何 |
| 底座右侧（x>3）与店前人行道偏空 | 全景右缘、街角前景 | 该区域只有路灯 / 垃圾桶，正适合放樱花树与电车 |
| **白天也在落雨，且与「樱花」主题抢戏** | 阶段5-亮色-全景：白天模式同样有雨丝 / 滴水 / 波纹 | `createRainSystem` 只按性能档给数量，`setTheme` 只换颜色**不换开关**——昼夜两套都常驻雨族 |
| **波纹很丑：粗黑灰圆环** | 阶段5-亮色-全景 路面上的深灰大圆环 | 三重问题叠加（详见 §4.6）：① `RingGeometry(0.72, 1)` 硬边粗环，无羽化；② 实例色 `setScalar((1-t)*0.28)` 最高只有 0.28——材质想做加法混合但**实际没设 `blending`**，走的是 NormalBlending，白×0.28 = 深灰，环越大越像「黑甜甜圈」；③ 最大半径 0.67m × 12 个，尺寸和密度都过大 |

**结论**：不是缺「贴图文件」，而是 (a) 材质未按部件分色、(b) 大表面缺程序化细节贴图（窗格 / 瓦面 / 分色带）、(c) 背景缺远景层、(d) 降水不分昼夜且波纹实现有 blending 错误。以下设计逐项对症下药。

## 2. 大致风格

延续《首页设计方案合集》§4 的**三渲二日式微缩雨景**，本轮把它从「白盒 + 少量霓虹」推进到「**有分色、有生活痕迹的上色成品**」：

- **基调不变，但降水换班**：白天 = 阴雨浅色阅读体验**且只落樱**（樱吹雪替代雨滴，风把瓣从树冠吹过人行道与路面）；夜晚 = 冷蓝雨夜 + 暖店内 + 霓虹，**只落雨**（雨丝、屋檐滴水、玻璃雨痕、波纹全部回来）。默认亮色，正文对比度不受影响。
- **降水与季节符号绑定**：白昼的动效语言是「春 · 樱」，夜晚的动效语言是「雨 · 灯」——两族粒子互斥，同一时刻只跑一族（性能也比现在「昼夜都跑雨」更省）。
- **波纹是夜雨的点缀，不是主角**：细、软、冷光、扩散即逝；白天路面上不再出现任何圆环。
- **色彩角色制**（新增的核心手法）——每个表面只承担一种角色，杜绝「到处刷白」：

| 角色 | 用途 | 色向 |
|---|---|---|
| 主角色 | 店面墙体、电车车身 | 暖奶油白 + 品牌深蓝 + 橙色点缀（从店招取色，保证与既有视觉同源） |
| 辅角色 | 邻栋、屋顶、路面 | 雾蓝灰 / 石板灰，明度低于主角色，衬托主体 |
| 点缀色 | 樱花粉、盲道黄、信号灯、贩卖机商品 | 小面积高饱和，控制在 ≤10% 画面占比 |
| 夜景点缀 | 窗格暖光、电车车内光、樱花树下的地灯 | 暖黄 / 淡粉 emissive，延续「冷暖对比」 |

- **细节贴图全部程序化**：窗格、墙裙分色带、瓦面、电车侧带文字，仍用 `CanvasTexture` 运行时生成（沿用阶段 4 的画布比例核对方法）。
- **樱花与电车都是「日式街角」符号**，与便利店主题自洽；电车走复古奶油 + 深蓝涂装，与店招同色系，不做抢眼的大红大绿。

## 4. 设计详解

### 4.1 A · 模型上色（分色 + 细节贴图）

#### 4.1.1 材质拆分（当前是最大问题）

现在 `mats.building` 一人分饰五角（店墙 / 屋顶 / 雨棚 / 邻栋 / 招牌底板）。拆成：

| 新材质名 | 用于 | 白天色 | 夜晚色 |
|---|---|---|---|
| `facade` | 店面主墙体（后墙、侧墙、屋顶底） | 暖奶油 `#f4efe4` | `mix(card, #3a4458, 0.72)` 再向暖偏移一点（保留暖底） |
| `facadeBand` | 墙裙分色带（墙体下 0.55m 一条） | 雾蓝 `#c5d2e0` | `#2f3b52` |
| `roof` | 店屋顶板、雨棚上表面 | 石板 `#9aa6b5` | `#39445a` |
| `neighbor` | 邻栋整体 | 蓝灰 `#b7c3d2` | `mix(ground, #2b3446, 0.7)` |
| `trim`（保留） | 框、杆、护栏 | 不变 | 不变 |
| `trunk` | 樱花树干 | `#6b4a3b` | `#4a3226` |
| `blossom` | 樱花树冠 | `#f6b6c2` | `#d9879b`（略降明度 + 微 emissive 粉 0.15） |
| `tramBody` | 电车车体 | 奶油 `#f2e8d8` | `#cfc6b8` 压暗 |
| `tramStripe` | 电车腰线 / 车顶 | 品牌深蓝 `#1d4e89` | 同色、微 emissive |
| `rail` | 轨道钢轨 | `#5b6472` | `#3c4454` |

**主题联动**：全部加进 `set`，在 `update(tokens)` 的 day / night 两个分支里赋值（和现有 `set.building` 同一套写法），保证切主题实时生效、不重建几何。

#### 4.1.2 程序化细节贴图（「贴图缺颜色」的第二半）

| 贴图 | 画布 | 内容 | 贴到哪 |
|---|---|---|---|
| `windowGrid` | 512×512 | 4×4 窗格：深蓝框 + 玻璃格（白天冷灰蓝、**夜里随机 40% 格子填暖黄 `#ffd9a8` 当灯**） | 邻栋四面（`MeshToonMaterial.map`，夜兼 `emissiveMap` 同一张） |
| `facadeTile` | 256×256 | 极淡横向砖缝（alpha 线条，不改大色） | 店面侧墙 / 后墙，`repeat(4,2)` |
| `tramLivery` | 512×128 | 深蓝腰线 + 「墨海電車 MOHAI TRAM」系统衬线字（沿用阶段 4 字体口径） | 电车两侧 `uprightPlane` |
| `petalSprite` | 64×64 | 单片五瓣花瓣（径向渐变粉，中心留白点） | 花瓣 `PointsMaterial.map` |

> 夜晚窗格直接抄阶段 4 的 `emissiveMap = map` 口径：一张图白天当固有色、夜里当灯箱，不维护两张画布。

#### 4.1.3 灯光微调（配合上色）

- 白天 `hemi 1.6 / key 1.4` 不动（阶段 2 实测过曝的教训），但把**最白的反照率压下来**（`facade` 不再是纯白），画面自然不发飘。
- 夜里给邻栋窗格加 `emissiveIntensity 0.55`，远景从「黑块」变成「亮着几扇窗的楼」，与设计文档 §4.3 夜景表「远景楼宇」的意图对齐。

### 4.2 B · 樱花树

#### 4.2.1 位置（按三个机位反推，沿用阶段 3 的方法）

> ⚠️ **本节坐标已被 §9 修订**（v3：用户要求樱花树迁至商店右后侧并高大化）。树的落位、体量、花瓣风向与灯光锚点一律以 §9 为准；本节保留为候选评估与历史决策记录。

候选点评估（机位坐标见设计文档 §5）：

| 候选 | 坐标 (x, z) | 全景 (5.2,4.6,5.2) | 街角 (3.8,1.7,3.2) | 橱窗 (2.2,1.5,2.4) | 结论 |
|---|---|---|---|---|---|
| 左前人行道角 | **(-3.05, 1.15)** | 视轴夹角 ≈10°，清晰入画、做左侧前景 | ≈28°，贴左缘入画、不挡店招 | ≈51°，不入画（橱窗镜头不该被树挡） | ✅ **推荐** |
| 店右侧（与电车抢位） | (3.3, -1.0) | ≈37°，基本出画 | 出画 | 出画 | ❌ 放了也看不见 |
| 店后 | (1.0, -3.2) | 被店体挡住 | 不入画 | 不入画 | ❌ |

**定案：`(-3.05, 1.15)`**，树干立在人行道上（`SIDEWALK_TOP=0.06`），树冠收在底座内沿之内；与自动贩卖机 `(-2.2, 0.85)`、路牌 `(-1.9, 1.55)`、信号灯 `(-3.2, 3.42)` 保持 ≥0.6m 树干净距，树冠允许与它们在画面上自然叠压（前景景深，设计文档 §2.3 的「前景」角色）。

#### 4.2.2 造型（全程序化）

- **树干**：主干 `CylinderGeometry`（下粗上细 r 0.09→0.055，高 1.35m），用 `rod()` 分 3–4 根斜枝（仰角 25°–45°），`trunk` 材质 + `outlineShell`。
- **树冠**：不要一个球——**7–9 个 `IcosahedronGeometry(0.42, 1)` 团块**摆成扁球冠（整体宽 ≈1.9m、高 ≈1.1m，中心 y≈1.9），每块随机 scale 0.75–1.15、绕 y 随机转角，`blossom` 材质；团块留缝，三渲二分档自然切出明暗面。可 `InstancedMesh` 压成 1 个 draw call。
- **树池**：根部一圈 `TorusGeometry(r 0.24, 管 0.035)` + 深色泥土圆片，泥土上撒 6–8 片静止花瓣贴片（`petalSprite` 的 `decal`，夜 `nightDim 0.9`）。
- **地灯（夜景点缀）**：树池旁 0.06×0.06×0.12 小射灯 + 暖粉 emissive；夜里配一盏低强度 `PointLight`（intensity 1.2、distance 2.4，挂 `LIGHT_ANCHORS` 新增 `sakura` 锚点），让樱花在夜景里仍是暖色主角。

#### 4.2.3 飘瓣动效（白天的「雨」，详见 §4.5）

- 新 `createPetalSystem(THREE, options)`（放 `rain-system.mjs`，与雨滴同一套 Points 模式），**只在白天运行**：
  - 数量：桌面 48 / 移动 24（比 v1 的 36 略加——它现在是白昼唯一的降水动效，承担全天氛围）。
  - **风场**：花瓣不再是「只在树附近打转」——生成点仍在树冠包围盒内，但叠加恒定风速 `vx = +0.18 ~ 0.32 m/s`（朝店前 / 路面漂），落地或漂出底座边界即回树冠顶重生。视觉读法：**风把瓣从树上吹过人行道、掠过路面**，一条从左前向右的粉色流。
  - 运动：`y` 匀速下落 0.24–0.40m/s；`x` 风速 + `sin(elapsed*1.1 + phase)` 摇曳；`z` 摇曳 ±0.14；`Points` 不支持逐粒子自旋，**接受无自旋**。
  - 落到底（y < 0.02）从树冠顶重生；`sizeAttenuation: true`，尺寸 0.045–0.07m。
- **与雨互斥**（v2 关键变化，不再「与雨共存」）：白天 `rain.group.visible = false`、`petals.points.visible = true`；夜晚反过来。切主题时用 0.35s opacity 淡入淡出，避免硬切闪烁。
- 主题切换时花瓣色跟 `blossom` 走（`setTheme(tokens)` 更新 `material.color`：白天 `#f6b6c2`、夜里即便不可见也同步到 `#d9879b`，防止切换瞬间闪色）。
- `prefers-reduced-motion`：花瓣冻结在初始随机态（与阶段 5 雨滴同一开关口径），画面仍有「树下落了一地瓣」的静态叙事。

#### 4.3.3 电车造型（程序化，两轴复古路面电车）

自下而上（单位 m，局部坐标，最后整体 `withGroup("prop:tram")` 摆位）：

1. **走行部**：底盘盒 `0.72 × 0.14 × 1.9`（`trim`）；两对车轮（`CylinderGeometry` r0.14 厚 0.06，轴沿 x）藏底盘两侧露一半。
2. **车体**：主盒 `0.78 × 0.86 × 2.0`（`tramBody` 奶油）；裙板第二只盒 `0.80 × 0.18 × 2.02`（`tramStripe` 深蓝）——比车身宽 2cm，三渲二下形成清晰蓝色腰线。
3. **车顶**：半圆柱 `CylinderGeometry(r 0.39, 长 2.0, thetaLength π)` 横放（`tramStripe` 同蓝）；顶上小盒空调 `0.4×0.1×0.7` + 受电弓（两根 `rod()` 折线，静态，**不接真接触网**——省一个动态约束）。
4. **窗带**：两侧各 4 扇 `uprightPlane` 用 `tramGlass`（`MeshToonMaterial` + emissive 暖白，白天 0.25 / 夜 0.9，复用饮料柜冷暖逻辑）；车头一扇大窗 + 两只圆头灯（夜里 1.1、白天 0.3）。
5. **侧带文字**：两侧 `uprightPlane(1.9, 0.16)` 贴 `tramLivery`（`decal`，夜 `nightDim 0.85`），位于裙板上方 0.1m。
6. **车门**：靠店一侧（+x 面）`0.55 × 1.1` 双开门缝贴片，静态关闭。
7. **描边**：车体 / 车顶 / 底盘走 `outline`（24° 阈值），圆轮与受电杆走 `outlineShell`。

**轨道**：两根长条盒 `0.05 × 0.025 × 3.6`（`rail`）在 x=2.27 / 2.83，顶面高于路面 0.012m；枕木 `InstancedMesh`（12 块 `0.66 × 0.02 × 0.12`，z 步进 0.3，暗木 `#7a6a58`）；轨间路面保持 `mats.road` 不开槽（沿用贴片抬高 0.012 的既有手法防 Z-Fighting）。

### 4.4 D · 背景天际线

- **远景楼宇剪影**：底座外 radius 8.5–11m 圆环上 24–32 个随机宽深盒体（宽 0.8–2.4、高 1.2–4.6），`MeshBasicMaterial`（不吃光、无描边）：
  - 颜色读 `--nmd-city`：白天 `rgba(62,82,112,0.2)` → JS 用现成 `cssColor()` 剥 alpha 设 `color`，`opacity = 0.2`；夜晚 `rgba(120,165,255,0.12)` 同理。
  - 夜里给 1/3 盒体贴 2–3 个暖黄窗点（同 `windowGrid` 口径，`decal` 夜 `nightDim 1` 不压暗），远景不死黑。
- 位置全在底座轮廓**之外**——三个机位看，它们只出现在底座边缘以外的天空区，不穿插进街区。
- 成本：共享一份材质 + `InstancedMesh`（每实例 scale 不同）⇒ 1 个 draw call。
- 降级：窄屏 / 低性能档楼宇数 32→16；reduced-motion 无影响（本就静态）。

### 4.5 F · 昼夜降水置换（白天落樱，夜晚落雨）

#### 4.5.1 问题

`createRainSystem` 的 `setTheme(tokens)` 目前只改颜色与透明度，**不改可见性**——雨丝、滴水线、玻璃雨痕、波纹在亮 / 暗两套主题下全部常驻。阶段 5 截图可证：亮色全景里同样有雨和波纹，与「樱花」这一春日符号抢戏，也浪费白天的 draw call。

#### 4.5.2 置换规则（单一事实来源：`tokens.scheme`）

| 子系统 | 白天（`scheme === "default"`） | 夜晚（`scheme === "slate"`） |
|---|---|---|
| 雨丝 Points | 隐藏（`visible=false`，update 跳过） | 显示，按性能档数量 |
| 屋檐滴水 `DRIP_LINE` | 隐藏 | 显示 + 沿线错峰重生 |
| 玻璃雨痕 | 隐藏 | 显示，向下扫掠 |
| 地面积水波纹 | 隐藏 | 显示，用 §4.6 新样式 |
| 湿地面 Reflector sheen | **保留但降档**：`opacity` 乘 0.55（刚下过雨的湿痕，不做主动雨效） | 全量，含真反射 |
| 花瓣 `petalSystem` | 显示（风场见 §4.2.3） | 隐藏 |

- **切换实现**：在 `rain.setTheme(tokens)` 与 `petals.setTheme(tokens)` 里各设 `visible`，并把「当前是白昼」存成 `rainSystem.isDay` / `petals.isNight` 布尔；`update()` 开头 `if (!points.visible) return`，隐藏时零计算。
- **淡入淡出**：不瞬切。`setTheme` 里启动 0.35s 的 `opacity` 线性过渡（雨族从当前值 → 0 或目标值），过渡中 `update` 仍跑；结束后落定 `visible`。复用阶段 5 已有的材质 `opacity` 字段，不新增 tween 库。
- **互斥不变式**：任一时刻 `rain 族可见 XOR 花瓣可见`；断言写在开发期注释里，验收用「亮色截图无雨丝 / 暗色截图无花瓣」二分检查。
- **滴水与波纹的从属**：它们是雨的派生效果，**跟随雨的可见性**，不单独决策——避免出现「没下雨却在冒波纹」的穿帮。

#### 4.5.3 为什么白天保留湿地面

白天虽然不落雨，但地面仍应读作「雨后 / 阴天湿润」：`wetGround` 的 sheen 与浅反射保留（`opacity × 0.55`），斑马线、路缘仍有微反光。这样樱吹雪落在的是**湿亮的路面**，花瓣粉色与湿灰路面的对比也比落在干路上更成立。完全关掉 Reflector 会让白天画面突然发干，与阶段 5 已验收的湿地面效果倒退。

### 4.6 G · 波纹美化（替换现状的「黑甜甜圈」）

#### 4.6.1 现状为什么丑（三条根因，全部要修）

| # | 根因 | 代码位置 | 视觉后果 |
|---|---|---|---|
| 1 | `RingGeometry(0.72, 1)` 硬边环，无羽化 | `rain-system.mjs` ripple 段 | 环缘刀切一样锐利，像贴纸不像水纹 |
| 2 | 想做加法混合但**没设 `blending: AdditiveBlending`**，实例色 `setScalar((1-t)*0.28)` 走 NormalBlending | 同上，`material` 构造处 | 白 × 0.28 = 深灰；环越大越像黑 / 深灰甜甜圈（亮色全景路面上那些大圆环即此） |
| 3 | 最大半径 0.67m、同时 12 个、寿命 1.25s | `RIPPLE_LIFE`、`0.12 + t*0.55` scale | 尺寸密度双大，抢路面的视线，不像点缀像污渍 |

#### 4.6.2 新设计目标（一句话）

**软、细、冷、快**——羽化双环贴图 + 加法混合冷光 + 缩小到 0.34m 内 + ease-out 扩散即逝；只在夜晚出现（白天被 §4.5 隐藏）。

#### 4.6.3 具体做法

1. **贴图换掉几何**：废弃 `RingGeometry`，改 `PlaneGeometry(1,1)` + 程序化 `rippleTexture`（`CanvasTexture`，128×128）：
   - **外环**：径向渐变，峰在 r≈0.68，环宽约 0.12 半径，两侧各 0.08 羽化 → 软环；
   - **内环**：峰在 r≈0.34、更细更淡（alpha 0.55），形成「双圈涟漪」——真实雨滴落地的经典读形；
   - **中心落点**：半径 0.15 的一点微光，模拟雨滴触地瞬间的亮点；
   - 整张贴图白色画在透明底上，颜色交给材质 `color`。
2. **混合模式**：`MeshBasicMaterial({ blending: THREE.AdditiveBlending, transparent: true, depthWrite: false })`。加法混合下实例色 `setScalar(brightness)` 从峰值淡到 0 即自然消失（修根因 2）；冷光色 `#9ec9ff`（夜雨的蓝白高光，呼应 `--nmd-wet`）。
3. **尺寸与密度**：`scale` 从 `0.10 + easeOutQuad(t) * 0.24`（最大边长 0.34m，约为现状一半）；数量 12 → 18（更小但更多，读作「细雨密纹」而非「几口大锅」）；寿命 `RIPPLE_LIFE` 1.25 → 0.9s。
4. **扩散曲线**：`easeOutQuad`（先快后慢）——水纹物理上也是扩散减速；亮度 `pow(1-t, 1.6)` 非线性衰减，前 30% 寿命最亮，后段拖尾消失。
5. **落点分布**：只撒在车行道 + 路缘（沿用现有 `z ∈ [1.95, 3.5]` 区间，x 收到 `[-2.6, 3.4]` 避开树池正下），y = `ROAD_TOP + 0.028` 防 Z-Fighting；确定性伪随机布点，截图可复现。
6. **降级**：移动档数量 18 → 10；`prefers-reduced-motion` 下波纹整族隐藏（它是纯动效，冻结无意义）；白天本来就隐藏（§4.5）。

#### 4.6.4 成本

- 几何从 `RingGeometry`（分段环带）换成两个三角形的 `PlaneGeometry`，三角形数反而下降；
- 材质仍是 1 个共享 `MeshBasicMaterial` + `InstancedMesh` ⇒ draw call 仍为 1，不占 §5 的 ≤40 预算增量；
- 多一张 128×128 `CanvasTexture`（≈64KB 显存），可忽略。

/* ---- rain-system.mjs：花瓣粒子（复用 createRainSystem 的 Points 结构，v2 含风场 + 昼夜可见性） ---- */
export function createPetalSystem(THREE, options) {
  const config = options || {};
  const count = config.count || 48;          // 移动端传 24；白天唯一降水，比 v1 的 36 略加
  const center = config.center || { x: -3.05, y: 2.0, z: 1.15 };
  const half = { x: 1.6, y: 1.2, z: 1.3 };   // 生成/重生仍锁在树冠 3.2×2.4×2.6 包围盒

  const positions = new Float32Array(count * 3);
  const speeds = new Float32Array(count);
  const phases = new Float32Array(count);
  const wind = new Float32Array(count);      // 每片恒定风速，vx ∈ [0.18, 0.32]
  for (let i = 0; i < count; i++) {
    positions[i * 3] = center.x + (Math.random() * 2 - 1) * half.x;
    positions[i * 3 + 1] = center.y + (Math.random() * 2 - 1) * half.y;
    positions[i * 3 + 2] = center.z + (Math.random() * 2 - 1) * half.z;
    speeds[i] = 0.24 + Math.random() * 0.16; // m/s 下落
    phases[i] = Math.random() * Math.PI * 2;
    wind[i] = 0.18 + Math.random() * 0.14;   // m/s 向 +x（店前 / 路面）漂
  }

  const geometry = new THREE.BufferGeometry();
  geometry.setAttribute("position", new THREE.BufferAttribute(positions, 3));
  const material = new THREE.PointsMaterial({
    map: config.map || null,                 // petalSprite CanvasTexture
    size: 0.06,
    sizeAttenuation: true,
    transparent: true,
    depthWrite: false,
    color: "#f6b6c2"
  });
  const points = new THREE.Points(geometry, material);
  points.name = "petals";
  points.frustumCulled = false;
  points.visible = true;                     // 白天可见，夜里隐藏（§4.5）

  let isDay = true;
  let fade = 1;                              // 0..1 淡变进度，setTheme 里驱动

  function setTheme(tokens) {
    isDay = tokens.scheme !== "slate";       // "default" = 白天
    // 目标可见性 + 0.35s 淡变（update 里把 fade 推向 isDay ? 1 : 0，到位后落定 visible）
    fadeTarget = isDay ? 1 : 0;
    material.color.set(isDay ? "#f6b6c2" : "#d9879b");
  }
  let fadeTarget = 1;

  function update(dt, elapsed, reducedMotion) {
    // 淡变：0.35s 线性推 fade，结束后落定 visible（互斥不变式：花瓣与雨族不同时可见）
    const fadeSpeed = dt / 0.35;
    if (fade < fadeTarget) fade = Math.min(fadeTarget, fade + fadeSpeed);
    else if (fade > fadeTarget) fade = Math.max(fadeTarget, fade - fadeSpeed);
    material.opacity = fade;
    points.visible = fade > 0.001;
    if (!points.visible) return;             // 隐藏时零计算
    if (reducedMotion) return;               // 冻结在初始随机态
    const attr = geometry.attributes.position;
    for (let i = 0; i < count; i++) {
      let x = attr.array[i * 3] + wind[i] * dt
            + Math.sin(elapsed * 1.1 + phases[i]) * dt * 0.18;
      let y = attr.array[i * 3 + 1] - speeds[i] * dt;
      let z = attr.array[i * 3 + 2] + Math.cos(elapsed * 0.9 + phases[i]) * dt * 0.14;
      // 落地或漂出底座边界 → 回树冠顶重生（风场循环）
      if (y < 0.02 || x > center.x + half.x + 2.5) {
        y = center.y + half.y;
        x = center.x + (Math.random() * 2 - 1) * half.x;
        z = center.z + (Math.random() * 2 - 1) * half.z;
      }
      attr.array[i * 3] = x;
      attr.array[i * 3 + 1] = y;
      attr.array[i * 3 + 2] = z;
      // z 向越界拉回（风只吹 x，z 仅摇曳）
      if (z > center.z + half.z) z = center.z - half.z;
      if (z < center.z - half.z) z = center.z + half.z;
    }
    attr.needsUpdate = true;
  }

  return {
    points: points,
    setTheme: setTheme,
    update: update,
    dispose: function () { geometry.dispose(); material.dispose(); }
  };
}

### 9.1 需求描述（用户原意）

**坐标约定**：「面对商店」＝观者站在店前（+z 侧，车行道／人行道上）朝 −z 方向看店。此时观者左手边为 −x，右手边为 +x，商店后方为 −z。

**需求一（电车位置）**：

> 电车的位置放在了商店门口，这不合逻辑。我希望电车的位置放在面对商店位置的左侧。这样的话电车就不会强占视觉中心。

- 现状问题：轨道 `TRACK_X = 2.55` 落在商店沿街立面（x ∈ [−1, 3]）的右段——车体 x ∈ [2.15, 2.95] 正对店招/海报区，读感是「电车堵在店门口」；且全景机位下电车仅偏离视轴约 8°，占据画面视觉中心。
- 期望：电车移到面对商店时的**左侧**（−x 侧），退出视觉中心，且不再停在商店门口。

**需求二（樱花树位置与体量）**：

> 樱花树太矮了太小了。我希望樱花树在面对商店位置在商店的右后侧。同时樱花树应该高大，这样的话可以形成遮蔽商店的视觉效果，比较有趣。

- 现状问题：树在 (−3.05, 1.15)，主干高仅 1.35 m、树冠中心 y ≈ 1.9、整树高约 2.5 m——与店高（檐口 2.6 m）齐平，既不「高大」也谈不上「遮蔽」。
- 期望：树迁到商店**右后侧**（+x 且 −z 方向，即观者右手边、商店后方的角落），大幅增高扩冠，树冠从上方罩住店顶，形成遮蔽关系。

### 10.1 现象确认（2026-09-25 实测复现）

### 10.2 根因（代码级）

问题不在渲染层，而在**构建树时「冠」和「枝」是两套互不参照的手写坐标**。具体三层：

1. **花冠为了「遮蔽商店」被整体推向 −x（这是 §9 的刻意设计，本身没错）**：树干定在商店右后侧 `SX = 3.32`（距底座右缘仅 0.28 m），而冠心定在 `CX = 2.35` —— 让花冠从上方盖住店顶右段。于是花球的可用范围被底座右缘（x ≤ 3.6）与店顶净空（y ≥ 2.76 + 球半径）双向夹住，**花球只能长在树干左侧**。
2. **枝端是另写一套硬编码坐标**：`prop:sakura` 里五条 `rod(a, b)` 的端点直接写成 `[2.42 … 3.02]`、`[3.0 … 3.5]` 这类数字，既没有引用花球表，也没有任何「必须落在花球内」的约束。结果枝端整体落在花球**外面**（见 §10.1 的覆盖余量表：枝1、枝4 完全在外）。
3. **验收探针只查了包围盒（AABB），而花球是球体**：早期验收口径是「冠的包围盒与枝端包围盒是否相交 / 冠是否在视锥内」。**包围盒相交 ≠ 覆盖** —— 花球是球，枝端可以是「在花球的 AABB 内、但离每颗球心都远于半径」。错位因此一路通过验收，直到用户从画面上看出来。

一句话概括：**冠是球，验的是盒子，枝是第三套坐标** —— 三者没有共享的几何约束，错位是必然的。

> 与「地基限界」「顶栏遮挡」的区别（避免再次误诊）：那两条说的是**树被裁掉一部分**（水平挤压 / 垂直遮挡）；本 bug 是**树完整地在画面里，但花没长在枝上**——所有几何都生成了、都在视锥内、都没有被裁剪。

### 10.3 修复方案（阶段 19）

**核心思路：把「花球表」升级为树形的唯一事实来源，枝端不再手写，而由花球中心反推——用构造保证「枝端必在花球内」。**

| # | 做法 | 说明 |
|---|---|---|
| 1 | **先定冠**：`SAKURA.blobs` 给出 18 颗花球的 `[x, y, z, scale]`（半径 = `blobR 0.55` × scale） | 分三层 + 干顶花团：下层 5 颗（y 3.28–3.42，其中左侧一颗伸到店顶右段上方维持「遮蔽商店」）、中层 5 颗 + 前后外扩 2 颗（y 3.52–3.88）、上层 4 颗 + 冠顶 1 颗（y 4.12–4.28）、干顶花团 1 颗 (3.24, 3.02, −1.60) |
| 2 | **枝端由花球反推**：`SAKURA.branches` 只声明「基部高度 + 目标花球下标 + 枝半径」，端点按 `tip = 球心 + (基部 − 球心) × (0.45 × r_blob / abs(基部 − 球心))` 计算 | 枝端到目标球心的距离**恒为 0.45 r_blob**，构造上必在球内；且枝的入冠段整根埋在花里，从任何机位都看不到「伸出花冠的秃枝」 |

### 10.8 二次返修：分叉点过高，树看起来「只剩一根」（2026-09-25）

> 本节记录 §10.3–§10.7 第一轮修复落地后用户的反馈 —— 「**为何现在樱花树只有一支了呢？**」的现象、原因与修正。
> **枝的基部高度与半径以本节为准**（§10.3 第 3 条、§10.5 R2、§10.6 第 1 条、§10.7 的 `branches` 表已按本节就地更新）；花球表、树位、冠的范围、花瓣发射盒、`CAMERA_KEYS[0]` 均不变。

#### 10.8.1 现象

第一轮修好「花没长在枝上」之后，树冠下方只剩**一根笔直的树干**，看不到分叉 —— 用户描述为「只有一支」。

| 返修前 | 返修后 |
|---|---|
| `阶段19-亮色-全景-返修前.png`（全景）、`阶段19-树形特写-返修前-只剩一根杆.png`（特写） | `阶段19-亮色-全景.png`（全景）、`阶段19-树形特写-修复后.png`（特写，同机位） |

#### 10.8.2 原因：第一轮把「枝端必在花球内」推成了「整根枝都在花球内」

1. 第一轮为了彻底消灭秃枝，把五枝基部**抬到 y 2.60–2.75**（几乎贴住干顶 2.85），并把枝端一律收进花球内部 0.45 r_blob。
2. 而花冠下沿在这一带只有 **y 2.69–2.86** —— §10.3 第 4 条已说明冠底受「店顶 2.76 + 球半径」约束，**不可能再低**（再低就穿屋顶）。
3. 两条叠加：**分叉点与整根枝身都落在花冠下沿之上**，于是枝被花球整根吞掉。实测五根枝的可见段只有 **0.00 / 0.00 / 0.00 / 0.08 / 0.16 m**，入冠 t = 0 ~ 0.18 —— 画面里自然只剩树干这一根竖线（外加干顶那截被花盖住的余量）。

> 本质是**验收指标只写了单边**：「枝端必须在花球内」防住了「秃枝」，却没有任何一条约束「枝身必须露得出来」。把单边指标推到极端（t → 0），枝形就消失了。

**与 §10.1 的原始 bug 不同**：原始 bug 是枝端跑到花球**外面**（秃枝）；这次是枝被花球**全部盖住**（无枝）。两个方向都要防。

#### 10.8.3 修正方案

只动枝的**基部高度与半径**，其余一切不动：

| 项 | 第一轮 | 返修后 | 理由 |
|---|---|---|---|
| 五枝基部 y | 2.60 / 2.70 / 2.70 / 2.65 / 2.75 | **2.15 / 2.35 / 2.40 / 2.30 / 2.20** | 把分叉点落到花冠下沿之下 0.3–0.6 m，分叉与枝身可见 |
| 枝半径 | 0.045 / 0.040 / 0.038 / 0.028 / 0.028 | **0.050 / 0.045 / 0.042 / 0.032 / 0.032** | 可见段变长后按原比例加粗，读起来才像树枝（仍远细于干径 0.13） |
| 枝端反推 | `tip = 球心 + (基部 − 球心) × 0.45 r_blob / abs(基部 − 球心)` | **不变** | 「枝端必在花球内」的构造保证保留 |
| 花球表 / 树位 / 冠 / 机位 / 花瓣盒 | — | **不变** | 本次不是布局问题，是枝的高度问题 |

**新增验收口径（补上缺的那一条）**：R2 由单边改为**双向**——

- 枝端覆盖余量 > 0（防秃枝，不变）；
- **可见分叉段 = 入冠 t × 枝长 ≥ 0.25 m**（防「枝被花吞掉」）。
